# 图片与二进制资源上传

负责人在开发进程 10 明确要求：后续不得再使用将整张图片编码塞入工具调用的方式。此前 Create Blob 确认框伴随“会话达到最大长度”，大体积 Base64 是怀疑原因，尚未拿到完整失败请求证明根因。

## 固定流程

1. 在本地准备实际图片文件，检查尺寸、格式、单文件预算与引用路径。编码压缩不得擅自改变负责人确认的画面。
2. 已有 Git 推送凭据时，用普通 `git add`、`git commit`、`git push` 上传功能分支，二进制通过 Git 协议传输。不要把凭据写进聊天或代码。
3. 无推送凭据时，用已登录 GitHub 网页的 **Add file → Upload files → choose your files**，通过文件选择器传入本地文件路径。先确认当前为自己的功能分支及正确目标目录。
4. ChatGPT Work 云浏览器使用共享文件路径：执行器 `/workspace/scratch/<相对路径>` 对应浏览器 `/home/oai/share/<相对路径>`。调用 `filechooser.setFiles` 时只传绝对路径，不读出或打印图片编码。
5. 等上传完成，在该功能分支提交。通过 GitHub 内容元数据或拉取分支，核对字节数和 Git blob SHA（本地 `git hash-object <文件>`）。仅看到进度条结束不算提交成功。
6. 所有文字修改可走 GitHub 插件；新增图片引用必须和图片本身一起进入最终 PR。删除旧资源时同时核对加载器、Workbox 预缓存和离线测试。

## 不可用时

如果文件通道或登录不可用，保留本地代码和图片，说明具体阻塞。不要降级回巨大的 Base64 工具调用，不要分片把编码塞进对话，也不要反复要求用户重发同一素材。

这条流程避免了图片数据进入对话与审批参数，不保证平台不会发生其他会话限制。
