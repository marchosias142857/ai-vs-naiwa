## 背景与边界

目前 `DungeonMap` 是房间之间的拓扑；室内仍是 `GRAYBOX_BOUNDS` 的 272×176 矩形。`DemoSession.rebuildRoom()` 根据 `layout:<floor>:<roomId>` 与可变的 `plans.length` 重抽，`DungeonRunState` 和入口检查点都没有模板 ID。扩充或重排目录可能改变旧档地形。凹形房间还会打破矩形门口、出生、导航、落石、跳跃及 Boss 撞柱判断。

GPT 负责统一几何、存档契约、地图美术生成和接入；Claude 复审并协调怪物 AI。武器机制、数值、碰撞箱归 Claude，武器贴图、浮空持械、特效及弹体外观美术与接入归 GPT，双方交叉复审，负责人拍板。#115–#119 不提前启动。

保持普通层 6 主路 + 2 支路共 8 房、Boss 层 2 房。100–200 是未来每层候选模板库容量；本项仅验证固定资源的组合能力，不交付 #115 的批量正式模板或不重复抽样。普通怪不恢复额外提示线，蓄跳蛙没有落点提示，Boss 既有提示保留。

## 提议 1：一份几何同时驱动物理与画面

新增纯数据 `RoomTemplate`（拟放 `data/roomTemplates/`）和纯查询 `RoomGeometry`（拟放 `sim/dungeon/`），不引入依赖、不导入 Phaser。字段名称以下为讨论稿：

| 字段                 | 用途与约束                                                                           |
| -------------------- | ------------------------------------------------------------------------------------ |
| `id`、`catalogId`    | 稳定字符串标识；发布后的碰撞、机关、门与锚点数据不可原地改写，修订生成新 ID/目录版本 |
| `theme`、`kinds`     | 主题和可用房间类型；旧 Boss 四柱与非战斗空房有独立模板                               |
| `bounds`、`interior` | 外包矩形和实际室内足迹；轮廓无自交、无零面积段，坐标有界                             |
| `solids`、`terrain`  | 墙/柱/池岸足迹及语义；装饰另列，不通过贴图 alpha 猜碰撞                              |
| `ports`              | N/E/S/W 可连接口的中心、朝向、触发段与安全入口点；不要求在外包框中点                 |
| `anchors`            | 入口、奖励/水晶、Boss 出生、普通出生候选区；含身体净空要求                           |
| `traps`、`decor`     | 机关的真实足迹/状态绑定与纯装饰放置；装饰变体不改变 sim                              |

首批只实现网格轴向边，宏观布局以 16 世界单位拼接，短收口可用更细网格。允许素材上的弧形岸沿/切角变化，实际不可行走侧必须清楚可辨，不能画出能通行的假缺口。可选 45° 只在后续通过验证后启用：细阶梯的水平、竖直步长都小于最小身体半径（当前蝌蚪为 3，可先试 2），并合并共线边、验证滑动不卡角；本草案不承诺斜碰撞已支持。

边界、柱体和门分别生成确定性的碰撞描述，供 Arcade 与 sim 查询消费同一份数据。Arcade world bounds 仅作外包框兜底，不能替代凹形边界。门通过既有锁门/向外移动规则切房；按拓扑方向选择可用 port，目标房用相反方向的安全入口。缺少所需方向或入口净空不足的模板在加载时拒绝，不能摆一扇假门。

边界池与内障碍池分开；编译模板时计算所需容量，超限报错，不沿用 `ROOM_BLOCKS=16` 静默截断。确切容量在原型编译报告后写入数据约束，帧循环不扩容。当前机关容量和近战命中位掩码保持既有上限。主城仍用 legacy 矩形适配器，保留门、祭台、出生与续玩行为。

### 原型尺寸与走位目标（均为草案，未碰撞验收）

首批共用现有坐标外包框 `(104,47,272,176)`，避免同时改镜头尺度与 AI 数值；表中是墙内几何，不含北墙立面、门外台阶或舷外水。

| 主题原型     | 可行走足迹的外包尺寸 | 轮廓构造草案                          | 加内障碍前的关键宽度                                  |
| ------------ | -------------------- | ------------------------------------- | ----------------------------------------------------- |
| 石殿宽 L 厅  | 272×176              | 矩形东北角去掉 64×64                  | 上部横向 208，右侧纵向 112                            |
| 沉船错位货舱 | 272×176              | 东北/西南角各去掉 32×32，破舷放在房外 | 中央完整 272×112，端部宽 240                          |
| 深渊浅凹厅   | 272×176              | 北侧中间凹入 64×48；北门择一侧直边    | 两侧各宽 104，下部完整 272×128                        |
| 奶池宽厅     | 272×176              | 弧形池岸放在室内轮廓外，保留四柱      | 四柱仍 22×22、中心偏移 ±76/±42；中间横向 130、纵向 62 |

尺寸不等于可用通道宽度：身体半径、柱、桶、门净空必须另算。普通主通路目标净地形宽度至少 96；Boss 四柱使用既有间距单独验收，不为满足目标偷偷移动柱子。若实际走位不足，先扩宽原型/移开新装饰，AI 数值调整交 Claude 与负责人。

现有参数核对：保持距离 110、横移距离 85、蓄跳蛙跳距 90、奶怪跳距 140、Boss 冲撞显示长度 220、普通出生最小距离 80（分别见 `data/enemies.ts`、`game/fx/hazardParams.ts`、`data/balance.ts`）。272 的横向跨度能容纳部分长距离动作，不代表每个方向都有相同净空；176 的高度也不能容纳完整 220 提示。应记录各原型实际扫掠/视线长度和各玩家位置的合法出生区，不用缩短 AI 数值掩盖地形问题。

### 足迹、可通行比例与遮挡

定义 `P` 为实际房间室内面积，包含内部柱、桶和内部水池的占地，排除墙体厚度、北墙立面、房外台阶、舷外水；不能把内部障碍挪出分母来凑比例。该验收状态下地形阻挡足迹（包括未破桶）的并集为 `S`，重叠部分只计算一次。设计目标 `area(P \ S) / area(P) ≥ 80%`，按碰撞数据计算，不从概念图估算。

另报每个身体半径的可达中心集合：将 P 向内缩半径、S 向外扩半径后求可行走区域。玩家半径 6 的最大连通区面积目标达到无内障碍时中心可用面积的 80%，所有有效门、交互点和主战斗区必须相连；同时公开相对 P 的绝对比例，不能混用两种口径。对各怪物半径也验证实际出现房型的通路，Boss 半径 14 单独验证。门锁定和桶未破时分别测量；临时敌群/落石另做压力场景，不拿它们的消失状态冒充初始净空。

低矮装饰在脚底层，不遮身体中心与危险提示；墙面/柱体以地面足点判深度，遮住靠墙角色的高墙盖层做局部淡化，透明不改变碰撞。Boss 四角与冲撞箭头保持现有可读层级。门框不可把入场点遮没，破舷画面缺口仍有完整的 `boundary` 碰撞。房间之外继续纯黑背景，水景仅在明确的近岸装饰带内，不能铺满视口。

## 提议 2：地形分类与 AI 查询

下表为拟定行为，尚未作为新玩法实施。现有地刺/水流/海草/地雷/桶的伤害、推力、减速和爆炸规则不随贴图重绘改变。

| 类别                                 | 挡身体       | 挡弹体                | 挡视线                        | 跳跃/出土/落石可落                  |
| ------------------------------------ | ------------ | --------------------- | ----------------------------- | ----------------------------------- |
| 房间外部、边界墙、锁门               | 是           | 是                    | 是                            | 否                                  |
| 内墙、石柱                           | 是           | 是                    | 是                            | 否                                  |
| 可通行地板、地面装饰                 | 否           | 否                    | 否                            | 是，须满足完整身体足迹              |
| 既有水流/海草/地刺等地面机关         | 否           | 否                    | 否                            | 按既有规则可落，机关效果保留        |
| 房外水池/舷外水/奶池岸外水景         | 按房间边界   | 按房间边界            | 按房间边界                    | 否；不新增水上活动                  |
| 未破桶                               | 是           | 保留既有命中/爆炸回调 | 是，保留 CombatWorld.los 规则 | 否                                  |
| 破桶装饰                             | 否           | 否                    | 否                            | 是                                  |
| 已落石块                             | 保留现行阻挡 | 保留现行阻挡          | 保留现行阻挡                  | 不允许新落石重叠；跳跃/出土落点避开 |
| 室内不可行走水池（预留、首批不启用） | 拟是         | 拟否                  | 拟否                          | 拟否；跨池跳跃/潜地须先协调         |

首批不把现有水流机关改成不可行走池，也不从概念图推导新水域玩法。室内水池的跨水攻击、跳跃和潜地规则需 Claude/负责人确认后另行启用。

建议接口如下，实际签名由 GPT 与 Claude 在本 ADR 评审时收敛。几何查询只读，不消耗 RNG、不发事件、不改变技能时间或移动状态；findPlacement 是调用这些查询的采样器，仅消耗调用者提供的既有随机流。结果写入调用者提供的固定对象，避免战斗帧分配。

| 查询                                       | 语义与调用者                                                                        |
| ------------------------------------------ | ----------------------------------------------------------------------------------- |
| `canOccupy(center, radius, purpose)`       | 检查完整圆足迹；purpose 区分 walk/spawn/land/surface/rock，不能只验中心点           |
| `sweepCircle(from, to, radius, mask, out)` | 检查整条胶囊路径；返回首个阻挡的位置、法线、距离和类别，用于移动/导航/技能落点      |
| `traceSegment(from, to, mask, out)`        | LOS、弹体/光束使用明确的掩码；凹口外部也算命中，不只查内墙                          |
| `findPlacement(request, rng, out)`         | 有限次随机候选 + 固定顺序的合法候选回退；返回失败而非任意初值；rng 由现有调用者提供 |
| `revision`                                 | 静态模板加动态阻挡的版本；切房、桶破坏、石块落地/消失后失效导航半径缓存             |

阻挡类别至少区分 boundary、wall、pillar、barrel、rock、water；相同命中距离按稳定物件 ID 决定，保证重放顺序。外包矩形不再用于猜测撞的是柱还是外墙。几何只报告命中，Boss 是否眩晕/撞碎仍由 sim 既有规则决定。旧目录先走现有适配器，迁移不能顺带改掉旧局行为。

### 请 Claude 在草案阶段确认的接入点

1. **铲爪蛙**：出土点用完整半径的 surface 查询；潜地阶段能否跨边界/柱/未来室内池需明确。GPT 提供查询，不自行重写潜地时序。
2. **跳跃与 stageView**：真实移动和显示共用一次确定的合法落点/扫掠结果，规定动态石块阻挡后的处理。`stageView` 只读；冻结、读档首帧、跳帧不能重抽。不能只把 Boss 四角挪到合法处却仍落在别处；蓄跳蛙不因此新增提示。
3. **远程与水域**：walk、LOS、projectile 掩码分开；首批水景在房外，未来室内池可否隔水射击按上表待确认项处理。
4. **Boss crashInto**：外边界/凹口不是柱，柱和落石保留现有撞晕与撞碎逻辑；相邻柱/边界/落石的首次命中优先级需与现有动作一致，不让装饰池岸误触发眩晕。
5. **无合法候选**：普通刷怪保留 pending，下一规则步重试，不生成墙内怪、不让波次提前结束；召唤/分裂/落石可跳过该次非法放置，但其随机消耗、数量和技能结束行为需 Claude 核对。不能无界重试、消耗别的随机流或推进模拟来找空位。

## 提议 3：稳定目录与两种存档

将当前 `ROOM_THEMES.plans` 的顺序、引用的 `ROOM_LAYOUTS` 数值、Boss 四柱、非战斗空房和矩形门口/锚点冻结为 `legacy_v1`。复制明确数据并锁定测试，不把可变的新目录当别名。修正旧布局必须新 ID；未来扩充不更改已有 ID 对应的碰撞、机关或门位。

新局使用不可变目录版本，例如 `modular_v2_0`。每局保存目录版本，进入一层时选定该层**所有**房间的模板 ID（含尚未访问的房间），数组按 `room.id` 对应；以后重建直接取 ID，绝不按当前数组长度重抽。扩充至 100–200 时新增目录版本，存量局的后续楼层继续使用开局目录，直到结束。抽样仍使用独立布局子流；#115 的不重复选择另做。

拟新增同一份纯数据到 `DungeonRunState.roomLayouts` 和 `FloorCheckpoint.roomLayouts`：

```ts
interface FloorRoomLayouts {
  catalogId: string; // 运行时按已安装的不可变目录枚举校验
  floor: number;
  templateIds: readonly string[]; // 长度严格等于该层 map.rooms.length
}
```

入口检查点保存它所指向的那一层的完整清单，而非上一层、当前单房或“下次再抽”的占位。`chooseUpgrade()` 当前先 nextFloor/showRoom 再 checkpoint，实施时在新层入场前生成清单，再复制到检查点；完整快照中的 `entry` 与 `sim.run` 的 floor/catalog/全部 ID 必须一致。深拷贝数组，不能用共享引用让旧入口副本随当前状态改变。

### 旧档迁移与恢复承诺

当前入口版本为 2（仍接受 1），完整快照版本为 2。提议升级入口和完整快照到 3，并保留独立的旧格式解析；存储写入成功才替换旧档。`parseSnapshot`/`saveFields` 的对象字段目前严格匹配，不能直接加可选字段放过未知内容；增加版本化字段表、已知目录/ID校验与跨记录校验，保持 zod/轻量解析一致。

存储键提议为 `avn.run.v3`：优先读 v3，无 v3 时才读现有 `avn.run.v2`/入口旧键；新快照 setItem 成功后才移除旧键，失败保留原档。发现损坏的 v3 不回读更旧副本复活进度，按其独立入口是否合法决定兜底或拒绝。死亡/通关清理全部相关版本键，继续保留 runId 结算去重。

缺少新字段只有在**合法旧版本**中才迁移：按原 `new Random(seed).fork('layout:<floor>:<roomId>').int(0, frozenPlans.length - 1)` 得到战斗房的旧 plan 序号并映射为稳定 ID；Boss 和 start/chest/exit 分别映射固定旧模板。目录冻结后反复迁移结果一致，不修改输入，不消耗战斗/掉落/升级流，不重放入房或刷怪事件。新版本缺字段、未知 ID/目录或错主题不能偷偷改成 v1。

```text
入口 v1/v2 { seed: S, floor: F, ...原字段 }
  → 入口 v3 { ...既有天赋/runId 迁移结果,
      roomLayouts: { catalogId: 'legacy_v1', floor: F,
                     templateIds: freezeV1(S, F, map.rooms) } }

同构建合法完整 v3：entry.roomLayouts == sim.run.roomLayouts
  → 用已存 ID 建房 → 恢复原 sim/game 记录，不重抽布局。

旧完整 v2，或 v3 的 build/dataHash 不兼容
  → 独立验证入口并迁移 → 明确提示“更新后从本层入口继续”；
    使用冻结目录和相同模板，不声称保住中途怪物/弹体/技能进度。
```

`runStorage.decodeRun` 当前已有 build/dataHash 不匹配时入口兜底的规则，本提议保留它，不越过构建兼容门槛硬装旧物理数据。因而本方案保障跨版本的布局与入口资源，**不承诺跨构建完整战斗进度恢复**。若负责人要求旧局原位置/波次继续，需要另列可验证的构建兼容迁移，不能靠放宽校验实现。

新版本字段损坏：完整 sim 无效但独立入口合法，按现行 invalid 提示退回入口；入口也无效则拒绝继续，不猜 ID、不静默清档。终局/已结算仍不可借入口副本复活。目录/模板几何、机关与门定义必须纳入版本兼容摘要；当前 `SAVE_VERSION.dataHash` 未列 `ROOM_THEMES`，实施时一起补齐。仅图像变化不得改模板几何 ID；是否能完整恢复仍遵从 build 校验。

## 模块美术与 200 布局资源验收

固定每主题一套地板变体、N/E/S/W 墙面、内外角、端帽、门洞、岸沿/破舷收口、柱/桶/机关状态和边缘装饰。光照方向固定，不用旋转一张带阴影墙图伪造四向。取消贝壳或其他重复徽记，保留已批准的宽敞战斗区。可选 45° 未启用时不依赖专用斜墙素材，弧形细节只作同组装饰组合。

生成/接入由 GPT 完成，原图与提示词进 `art-src`，运行时图集进 `public/assets`；按仓库文件通道上传二进制并核对 blob、字节和哈希。本 ADR 没有生成新图，没有把概念整图当房间背景。

在固定纹理 key/frame 集合下组合至少 200 个可区分布局作为容量 fixture：差异必须涉及轮廓、门或障碍布置，不能只改 ID/颜色凑数。记录所有布局引用的资源集合相等/为固定集合子集、无缺帧、无每房专用背景。逐布局连通/净空/容量检查，轮换实例时纹理和显示对象数量不能单调增长。这是素材系统能力验收，fixture 不注册为正式 #115 内容。
