# 0019. 完整局面存档（存档第 2 版）

- 状态：提议（第 3 稿；第 2 稿按 GPT 评审修订，第 3 稿区分兜底提示）
- 提出者：Claude
- 批准：负责人（合并即批准）
- 关联：Issue #62；负责人决定见 #33 评论；取代 ADR 0014 的「只存楼层入口」

## 背景

负责人决定：中途退出后，从退出那一刻的状态继续。手机上的「退出」经常不是玩家主动的：来电、切 App、系统在后台杀掉网页。这时如果回到楼层入口或房间入口，玩家就白打了一场。

负责人同时确认了三点：

- 飞行中的子弹也要保存，恢复后要和没中断时一样；
- 恢复时如果正在战斗（门锁着），先显示 3 秒倒计时，期间时间完全停止；不在战斗中就直接继续；
- 暂停后退出、关页面、切到后台，三种情况都要保存。

ADR 0014 的楼层入口检查点只保存种子、升级、武器、资源和成绩，不保存房内状态和随机流，满足不了这些要求。

## 决定

### 1. 存档格式

新 key 为 `avn.run.v2`，内容是一个 JSON 对象，`version: 2`。原则是只存「不能由种子和 data 重新算出来」的东西。顺序会影响结果的集合，一律按原顺序存成数组，不能当作无序集合。

**`meta`**

- 种子、构建号（`build`），以及数据指纹（`dataHash`，由武器、攻击、敌人、角色、掉落、地牢、房间规则等 data 计算）；
- 保存时间：只用于菜单显示，不参与逻辑。

**`entry`**

- 本层入口的检查点，格式同 ADR 0014。它是**真正进入本层那一刻**在内存里取下的独立副本，之后每次保存都原样带上，不能在退出时用当前资源重新生成。

**`sim`**（纯 sim 状态，由各 sim 模块自己导出）

- `CombatWorld`：
  - `time`、`nextId`、`playerDied`；
  - 玩家武器状态：当前与第二把武器、冷却、连发剩余与间隔、移动调校、最后移动方向、冲刺方向；
  - `PlayerResources` 全部字段，包括内部的修复计时；
  - 自动瞄准的当前目标与下次换目标的时间。
- 实体记录：按 `actors` 数组原顺序保存，包括等待回收的尸体。每条记录存编号、阵营、种类、阶段、位置、自主速度、生命与上限、无敌状态与截止时间、出场时间、击退的全部字段、AI 大脑、预警标记、移动速度、接触伤害、朝向。
- 子弹记录：存编号、阵营、发射者编号、**来源定义 ID**（玩家武器或敌方攻击）、角度、伤害（已乘升级倍率）、暴击率、击退、剩余穿透、已命中列表。来源 ID 是为了让 game 能重建碰撞半径与外观：发射者可能已经换枪或被回收，从它当前的状态反推不出来。sim 的子弹表只按编号查找、不遍历，所以内部顺序无关。
- 每一条随机流的当前状态，如 `spread`、`crit`、刷怪种类与位置、掉落、升级候选。
- `DungeonRun`：楼层、房间、阶段、探索 / 清理 / 宝箱标记、波次、波次计时、存活数、成绩。
- `RoomDirector`：当前楼层与待刷数（#57 的容量保护）。
- `LootSystem`：按原顺序的全部槽位，以及当前房间。
- 本局的升级序列，以及出口三选一时的候选列表。

**`game`**（表现层里会影响之后结果的状态，由 game 导出）

- 子弹池：每个槽位按池中顺序存「空闲」或子弹编号，并存该槽物理体的位置、速度、碰撞半径和剩余寿命；同时按原顺序保存空闲栈。
- 角色池：每个槽位按池中顺序存角色编号，以及该角色物理体的实际位置和速度。以物理体为准，不能用 `ActorView.vx/vy` 代替：例如换房时 `RoomArena.teleport` 会把物理体速度清零，但 sim 里上一步给出的速度不会变。
- 每个尸体剩余的死亡表现时间：它决定实体记录何时回收，见 ADR 0017。
- 胜负结算的等待计时：只作为内部字段，见第 2 节「终局」。

**顺序为什么要保留**：Phaser 的组对组碰撞按 `group.getChildren()` 的顺序处理。同一物理步里有多颗子弹命中时，处理顺序决定暴击随机数的消耗顺序，以及谁先触发无敌、谁先死。所以恢复时子弹和角色必须回到**原来的槽位**，空闲栈也要按原顺序恢复；sim 的 `actors` 顺序同样保留。

**不保存的东西**：

- 地图（种子 + 楼层）、房间布局、导航缓存（查询结果与缓存无关）、显示对象、音效；
- Arcade 固定步长的时间累加器：恢复时清零；
- 输入：暂停与恢复时统一丢弃，见第 3 节。

**一致性的定义**：两局面对**同样的物理步输入序列**结果相同，而不是「同样的渲染帧数」。

### 2. 何时保存

保存入口只有一个，可以重复调用：先取齐全部字段，然后一次 `setItem`。

**触发时机**：

- 进入新楼层；
- 进入手动暂停时：提前保存一份，缩小暂停后直接关页面的风险窗口；
- 暂停菜单点「退出」时：先保存，再切回菜单，不能等对象池 shutdown 之后；
- `visibilitychange` 变为 hidden（主要保存点）和 `pagehide`（补充）。两者先后顺序不确定，都调用同一个保存入口。必须在事件回调里同步完成取快照、`JSON.stringify` 和 `localStorage.setItem`，不能 await，也不能排到下一帧或空闲回调。现有 `LifecycleService` 先暂停再调用 `onHidden`，正好在这里同步取快照。

**一致性边界**：只在完整更新的边界取状态，不在 WORLD_STEP 监听链的中途取，所以不会存下半步的状态。

**做不到的事**：移动端进程被直接杀掉或崩溃时，可能不会再有任何 JS 回调。本方案保证「观察到上述事件就立即保存」，不保证任意强杀都能存到最后一刻。没有比 hidden 更晚又更可靠的关闭事件，也不需要因此改用异步存储。

**写入失败**：保留上一份有效存档，不删除、不覆盖。只有 v2 写入成功后，才删除旧的 v1。存储不可用时照常游玩，与 v1 相同。

**终局**：死亡或通关时删除存档。进入结算（`finished`）之后，hidden、pagehide 或重复事件只能清理存档，不能再生成一份可继续的存档；`RunPersistence` 的成绩写入只执行一次，从 BFCache 返回时也不重复。保存的结算等待计时不会让已结束的局重新变成可继续。

### 3. 恢复、暂停与输入

**恢复流程**（先恢复，后开放）：

1. 菜单「继续」：用同一种子新建 sim 与场景对象，但**不走开局流程**。不调用会清空东西或发事件的路径，例如 `showRoom` → `loot.enterRoom`（清空物资）、`arena.teleport`（清空子弹）、出生与刷怪。
2. 按快照覆盖 sim，重建当前房间的墙体与布局，把子弹和角色放回原槽位，重设物理体的启用状态、圆形尺寸、坐标与速度。
3. 恢复期间不发任何业务事件：不重发掉落、击杀、开火、清房、结算。`load` 只写状态。
4. 全部恢复完成后，才开放保存与输入。这样新建对象时的初始状态不会被当成入口检查点，覆盖掉原来的 v2。

**暂停原因**：恢复倒计时是一个**独立的暂停原因**，与手动暂停、切后台、竖屏、升级三选一、胜负结算并列。

- 物理只在**没有任何暂停原因**时推进。倒计时结束只释放它自己的原因，其他原因还在就继续暂停。
- 例：在出口三选一时存档。恢复后 `locked` 为假，所以没有倒计时，但升级选择本身仍然让物理保持暂停。
- 实现上，由 game 层用一个暂停原因集合统一控制 `physics.pause / resume`，各处不再直接调用。

**倒计时规则**：

- 只在 `DungeonRun.locked` 为真时出现，时长 3 秒（`RESUME_RULES.countdown`，放进 data 并带 schema）。
- 期间不触发 WORLD_STEP，sim 完全不推进，包括护甲修复、技能冷却、子弹飞行。画面停在快照那一刻，让玩家看清怪物和子弹的位置。
- 按真实时间计时。它只是界面计时，不推进 sim，所以不违反 ADR 0004。
- UI 保持更新：暂停键和暂停菜单（继续 / 退出）照常可用，被忽略的只是玩法输入。
- 倒计时期间如果出现手动暂停、切后台或竖屏，等这些原因全部解除后，倒计时从 3 重新开始。
- 重置倒计时和清空输入必须在生命周期恢复的回调里、`game.loop.wake()` 之前完成。`wake()` 会立即跑一帧，不能等到之后的 `scene.update` 才重置。
- 从 BFCache 回来（`pageshow` 且 `persisted`）时复用现有的局，不重新 `load`，也不重复注册监听。
- 倒计时的视觉由 Claude 在画面方案里给出。

**输入清理**：现在有三处会锁存玩法输入，`controls.reset()` 或 `bridge.setInput(empty)` 都清不掉已经锁存的边沿：

- InputController / InputState：按键集合、边沿、手柄状态；
- `CombatBridge`：`skillPressed`、`swapPressed`、`interactPressed`、`pausePressed` 用 `||=` 锁存；
- `DemoSession.interact`：单独锁存。

进入和结束恢复冻结时，以及每一次暂停与恢复时，这三处都要清空。冻结期间不锁存任何玩法动作。手柄持续按着的键要先回到中立位置才重新生效（沿用现有的 `padBlocked` 机制）。否则倒计时一结束，就可能立刻冲刺、换枪或拾取。

输入边沿不存档：暂停与恢复时统一丢弃，不属于逐物理步一致性的保证范围。

### 4. 校验与兼容

**解析方式**与 ADR 0014 一致：在 sim 里手写轻量校验，不把 zod 打进战斗包；`data/schema/save.ts` 里有对应的 zod schema，两者用成对测试保证一致。校验失败就**整份拒绝**，不擅自夹取或修正数值，因为那会改变局面。

**按字段校验**，不沿用 v1「资源字段全部非负」的规则：

- **数字**：一律要求有限，拒绝 NaN 和 Infinity。符号与范围按字段的含义定，在 schema 里逐个标注：
  - 允许负数：速度、朝向与角度、击退和冲刺方向、AI 大脑的冷却与计时（`moveEnemy` 每步都会让 `brain.cooldown -= dt`，追击怪的冷却可以低于零）；
  - 有范围约束：生命在 0 到上限之间，上限为正；护甲、能量在 0 到各自上限之间；金币、成绩、各种时长不小于 0。
- **定义 ID**（武器、攻击、敌人、角色、升级、掉落种类）：必须在当前 data 里存在，否则拒绝。
- **实体编号**：
  - 必须是 1 到 `nextId - 1` 之间的整数；
  - 存活实体和存活子弹的编号各自唯一；
  - 子弹的 `ownerId` 和已命中列表**可以指向已经回收的实体**：发射者死了子弹还在飞，或者穿透弹打死并回收了第一个目标后继续飞，都是正常情况。只检查编号在已分配的范围内，不要求它还在 `actors` 里。
- **不变量**：
  - 实体数不超过 `maxActors`，子弹数不超过 `maxBullets`，掉落数不超过槽位容量；
  - 阶段是合法枚举；
  - 玩家记录恰好一条；
  - 房间编号在地图范围内，探索 / 清理 / 宝箱标记数组与房间数一致；
  - sim 的存活子弹与 game 子弹池里的占用槽位一一对应。

**分工**：sim 校验 `sim` 部分；game 校验 `game` 部分，并负责两边的交叉检查（子弹编号一一对应、角色槽位与 sim 实体对应）。

**兜底规则**：

兜底时，`entry` 一律按当前 ADR 0014 的规则**单独校验**。三种情况的提示分开写：

- `build` 或 `dataHash` 与当前版本不一致（例如 PWA 更新改了数值），`entry` 有效：从本层入口继续，菜单提示「游戏已更新，从本层入口继续」。
- 版本一致，但 `sim` / `game` 部分校验失败，`entry` 有效：从本层入口继续，菜单提示「存档异常，从本层入口继续」。
- 整份 JSON 损坏，或 `entry` 缺失或也校验失败：不能继续。菜单回到「没有可继续的存档」状态，并提示「存档已损坏，无法继续」。

读到旧的 `avn.floor.v1` 时，按 ADR 0014 从楼层入口继续；下一次 v2 写入成功后删除 v1。

### 5. 一致性要求与测试

核心要求：**存档再读档，与不中断一直玩，面对同样的物理步输入，结果完全相同。**

**sim 层（精确比较）**：

- 多个种子、随机输入，先跑 K 步，存档并经过 JSON 序列化，再读入一套全新的对象；两边用同样的输入再跑 M 步，比较完整快照和事件日志，要求逐项相等。
- 要覆盖的情况：
  - 战斗中、出口三选一、Boss 阶段切换；
  - 尸体待回收、满池；
  - 合法的负速度与负 AI 冷却；
  - 发射者或已命中目标已经被回收的子弹（存档往返后仍然有效）。
- 这条测试同时用来防止以后漏存：新增 sim 状态却没写进快照，两边结果就会分叉，测试失败。

**浏览器层（真实 Arcade，同样的物理步输入）**：

- 比较存读档前后的命中与伤害事件，覆盖：不同半径的飞行子弹、同一物理步里多颗子弹命中、满池回收后再分配的槽位、待回收的尸体。
- 保存时机：
  - pagehide 单独触发、hidden 单独触发、hidden 之后紧跟 pagehide；
  - 暂停后退出；
  - 进入手动暂停时的提前保存；
  - 从 BFCache 返回。
- 失败与终局：写入失败时保留旧档；结算后不会复活成可继续的存档；成绩只记一次。
- 倒计时：
  - 战斗中恢复，3 秒内 WORLD_STEP 次数、所有物理位置与子弹剩余寿命都不变；
  - 非战斗房间没有倒计时；
  - 在出口三选一时恢复，仍停在选择界面；
  - 倒计时到 2 秒时分别手动暂停、切后台、转竖屏，回来后重新完整计时 3 秒。
- 输入：0 个物理步时已锁存的冲刺 / 换枪 / 拾取边沿，在暂停、存档、恢复后都不会触发；持续按着的手柄键要回中立后才生效。
- 兼容：版本或数据变化、局面校验失败都走入口兜底，提示各不相同；JSON 损坏时无法继续；存储被禁用时仍可开局。

### 6. 接口

- `Random`：在已有的 `snapshot` 之外，新增 `restore(state)`。
- 各 sim 模块（CombatWorld、DungeonRun、LootSystem、RoomDirector、AutoAim、PlayerResources）新增 `save(): XxxState` 和 `load(state)`。状态是纯 JSON 对象，`load` 不发事件。CombatWorld 的这两个方法写进 `api.ts`。
- sim 子弹记录新增来源定义 ID（见第 1 节）。`BulletSpawn` 不变。
- 新增 `src/sim/run/snapshot.ts`，负责组装与解析 `sim` 部分；新增 `src/data/schema/save.ts`。
- 帧循环里不调用这些方法；它们只在保存或恢复时分配对象。

## 影响

- **sim（Claude）**：第 6 节的接口、子弹来源 ID、`sim` 部分的解析与 sim 层一致性测试。
- **game / services（GPT，等本 ADR 批准后开始）**：
  - `game` 部分的快照与校验（槽位顺序、物理体状态、死亡计时）；
  - 暂停原因集合；
  - 恢复流程（不走开局路径、不发事件）；
  - 三处输入清理；
  - 各保存时机的同步写入；
  - 菜单「继续」改读 v2，以及两种失败提示；
  - 倒计时界面；
  - 浏览器层测试。
- **体积与耗时**：子弹满 500 颗时约 50 KB（估算），远低于 localStorage 上限。同步保存的总耗时（取快照 + 序列化 + `setItem`）由 GPT 在真机上测量，目标是 10 ms 以内；超出时再讨论压缩字段名。
- **以后的约束**：凡是新增会影响结果的 sim 或 game 状态，都必须写进快照；格式有不兼容的改动时，提升 `version` 并补新 ADR。
- **回退方式**：删除 `avn.run.v2` 的读写，恢复 ADR 0014 的入口检查点即可。v1 的解析代码保留到 v2 稳定之后。

## 备选方案

- **只存房间入口**：实现简单，但战斗中退出要重打本房，不符合负责人「从退出时继续」的要求。
- **录像回放**（只存种子和全部输入，读档时重放）：存档很小，但读档要从头重放，耗时随游戏时长增长；而且 Arcade 的结果依赖重放环境，难以保证一致。
- **不存子弹**：Boss 弹幕在场时差别明显，也做不了精确的一致性测试。负责人已确认要存子弹。
- **让命中顺序与池历史无关**（例如每步按编号排序处理碰撞）：恢复时就不用保留槽位顺序，但要改动现有的碰撞流程，还会改变当前的战斗结果。保存槽位顺序的改动更小。
- **恢复后停在暂停界面**：负责人改为「战斗中 3 秒倒计时，不在战斗中直接继续」。
