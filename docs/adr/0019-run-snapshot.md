# 0019. 完整局面存档（存档第 2 版）

- 状态：提议
- 提出者：Claude
- 批准：负责人（合并即批准）
- 关联：Issue #62；负责人决定见 #33 评论；取代 ADR 0014 的「只存楼层入口」

## 背景

负责人决定：中途退出后，从退出那一刻的状态继续。手机上的「退出」经常不是玩家主动的——来电、切 App、系统在后台杀掉网页——所以回到楼层入口或房间入口都会让玩家白打一场。

负责人同时确认了三点：

- 飞行中的子弹也要保存，恢复后要和没中断时一样；
- 恢复时如果正在战斗（门锁着），先显示 3 秒倒计时，期间时间完全停止；不在战斗中就直接继续；
- 暂停后退出、关页面、切到后台，三种情况都要保存。

ADR 0014 的楼层入口检查点只保存种子、升级、武器、资源和成绩，房内状态和随机流都不保存，满足不了这个要求。

## 决定

### 1. 存档格式

新 key 为 `avn.run.v2`，内容是一个 JSON 对象，`version: 2`。内容分四部分，每部分都只存「不能由种子重新算出来」的东西：

- `meta`：种子、构建号（`build`）、数据指纹（`dataHash`，由武器 / 敌人 / 掉落 / 地牢等 data 计算）、保存时间（只用于菜单显示，不参与逻辑）。
- `entry`：本层入口的 ADR 0014 检查点，原样内嵌，作为兜底（见第 4 节）。
- `sim`：纯 sim 状态，由各 sim 模块自己导出：
  - `CombatWorld`：`time`、`nextId`、`playerDied`、玩家武器状态（当前 / 第二把、冷却、连发剩余、移动调校、最后移动方向、冲刺方向）、`PlayerResources` 全部字段（含内部的修复计时）、自动瞄准的当前目标与下次换目标时间；
  - 全部实体记录，包括等待回收的尸体：编号、阵营、种类、阶段、位置、自主速度、生命、无敌、出场时间、击退、AI 大脑、预警标记；
  - 全部存活子弹记录：编号、阵营、发射者、角度、伤害、暴击率、击退、剩余穿透、已命中列表；
  - 每一条随机流的当前状态，如 `spread`、`crit`、刷怪种类 / 位置、掉落、升级候选；
  - `DungeonRun`：楼层、房间、阶段、探索 / 清理 / 宝箱标记、波次、波次计时、存活数、成绩；
  - `RoomDirector`：当前楼层与待刷数（#57 的容量保护）；
  - `LootSystem`：全部槽位与当前房间；
  - 本局升级序列，以及出口三选一时的候选列表。
- `game`：表现层里会影响之后结果的状态，由 game 导出：
  - 每颗子弹的物理位置、速度、剩余寿命；
  - 每个尸体剩余的死亡表现时间（它决定实体记录何时回收，见 ADR 0017）；
  - 胜负结算的等待计时。

不保存可以重建的东西：地图（种子 + 楼层）、房间布局、导航缓存（结果与缓存无关）、显示对象、音效、输入边沿。

### 2. 何时保存

- 进入新楼层时，替代原来的 v1 入口检查点；
- 暂停菜单点「退出」时；
- `pagehide`，以及 `visibilitychange` 变为 hidden 时。iOS 切后台后可能直接杀掉页面，所以这两处必须在事件回调里同步写入 localStorage，不能 await。

保存只发生在两次渲染帧之间（DOM 事件里），不会发生在物理步中途，所以不会存下半步的状态。

死亡或通关时删除存档。存储不可用时照常游玩，与 v1 相同。

### 3. 恢复与倒计时

菜单「继续」→ 用同一种子新建一局 → 按快照覆盖 sim 与 game 状态 → 检查房间是否在战斗中：

- **战斗中**（`DungeonRun.locked` 为真）：显示 3 秒倒计时。这期间物理世界保持暂停，不触发 WORLD_STEP，sim 完全不推进（包括护甲修复、技能冷却、子弹飞行），输入也被忽略。画面显示冻结的局面，让玩家看清怪物和子弹的位置。倒计时结束后恢复物理，开始推进。
- **不在战斗中**：直接继续，没有倒计时。

倒计时按真实时间走，它只是界面计时，不推进 sim，所以不违反 ADR 0004。倒计时期间切到后台或手动暂停，回来后重新从 3 开始。倒计时时长放进 data（`RESUME_RULES.countdown = 3`，带 schema），由负责人调整。倒计时的视觉由 Claude 在画面方案里给出。

### 4. 校验与兼容

- 解析方式与 ADR 0014 一致：在 sim 里手写轻量校验，不把 zod 打进战斗包；data/schema 里有对应的 zod schema，两者用成对测试保证一致。版本不对、未知 ID、非法数字（NaN、Infinity、负数、越界编号）一律拒绝。
- `build` 或 `dataHash` 与当前版本不一致（例如 PWA 更新改了数值），或者快照本身校验失败时，改用内嵌的 `entry` 从本层入口继续，菜单写明「游戏已更新，从本层入口继续」。
- 读到旧的 `avn.floor.v1` 时，按 ADR 0014 从楼层入口继续；下一次保存写入 v2，并删除 v1。

### 5. 一致性要求与测试

核心要求：**存档再读档，与不中断一直玩，结果完全相同。**

- sim 层（精确比较）：多个种子、随机输入，先跑 K 步，存档并经过 JSON 序列化，再读入一套全新的对象；然后两边用同样的输入再跑 M 步。比较双方的完整快照和事件日志，必须逐项相等，覆盖战斗中、出口三选一、Boss 阶段切换、尸体待回收、满池等情况。
- 这条测试同时用来防止以后漏存：新增 sim 状态却没写进快照，两边结果就会分叉，测试失败。
- game 层（浏览器测试，允许小误差）：战斗中触发 pagehide 存档 → 重新载入 → 继续 → 倒计时 3 秒内时间不动 → 之后正常推进；非战斗房间没有倒计时；存储被禁用时仍可开局。

### 6. 接口

- `Random`：在已有的 `snapshot` 之外，新增 `restore(state)`。
- 各 sim 模块（CombatWorld、DungeonRun、LootSystem、RoomDirector、AutoAim、PlayerResources）新增 `save(): XxxState` 与 `load(state)`，状态是纯 JSON 对象。CombatWorld 的这两个方法写进 `api.ts`。
- 新增 `src/sim/run/snapshot.ts`：组装与解析 `sim` 部分；新增 `src/data/schema/save.ts`。
- 帧循环中不调用这些方法；它们只在保存或恢复时分配对象。

## 影响

- sim（Claude）：上面列出的 save / load 接口、快照解析与一致性测试。
- game / services（GPT，等本 ADR 批准后开始）：
  - game 部分的快照；
  - 在暂停退出、pagehide、hidden 三处同步写入；
  - 菜单「继续」改读 v2；
  - 倒计时界面与冻结逻辑。
- 存档体积：子弹满 500 颗时约 50 KB，远低于 localStorage 上限。同步写入的耗时由 GPT 在真机上测量，目标是 10 ms 以内；超出时再讨论压缩字段名。
- 以后凡是新增会影响结果的 sim 或 game 状态，都必须写进快照；格式有不兼容的改动时，提升 `version` 并补新 ADR。
- 回退方式：删除 `avn.run.v2` 的读写，恢复 ADR 0014 的入口检查点即可；v1 的解析代码保留到 v2 稳定之后。

## 备选方案

- **只存房间入口**：实现简单，但战斗中退出要重打本房，不符合负责人「从退出时继续」的要求。
- **录像回放**（只存种子和全部输入，读档时重放）：存档很小，但读档要从头重放，耗时随游戏时长增长；而且 Arcade 物理的结果依赖重放环境，难以保证一致。
- **不存子弹**：Boss 弹幕在场时差别明显，也无法做精确的一致性测试。负责人已确认要存子弹。
- **恢复后停在暂停界面**：负责人改为「战斗中 3 秒倒计时，不在战斗中直接继续」。
