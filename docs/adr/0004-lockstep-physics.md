# 0004. 战斗 sim 按物理步锁步推进

- 状态：提议
- 提出者：Claude
- 批准：负责人（合并即批准）
- 关联：ADR 0003、PR #24（实测）、PR #26（bridge 实现）、Issue #15（接线）

## 背景

ADR 0003 约定的顺序是「在战斗场景的 update 中，每个渲染帧调用一次 `step`」。Arcade 默认用 60 Hz 固定步长推进物理，渲染帧率与它不同步时，一帧里可能有 0 个或多个物理步。

PR #24 实测：按渲染帧调用 `step` 时，击退距离随帧率变化（数据为 4 px，120 fps 时 4.43 px，144 fps 时 3.92 px）。原因是 sim 计算速度时用的时间，与物理实际按这个速度移动的时间不相等。

## 决定

1. **sim 在 Arcade 的 `WORLD_STEP` 事件里推进**，每个物理步一次，`dt` 取物理步长。顺序（`CombatBridge.tick`，PR #26）：
   子弹寿命 → `syncPosition`（读 `body.center`）→ `step` → 清除输入边沿 → 设置速度 → 生成子弹。
   `WORLD_STEP` 在本步移动和重叠检测之后发出，所以写回的位置已经包含这一步的移动和碰撞，设置的速度用在下一步。
2. **输入每个渲染帧采样一次**：战斗场景在 PRE_UPDATE（早于 Arcade 推进物理）调用 `controls.sample()`，交给 `bridge.setInput()`。bridge 复制一份，并锁存 `*Pressed` 边沿：本帧没有物理步时留到下一帧，有多个物理步时只交给第一步。
3. **其他按时间推进的玩法逻辑也挂在 `WORLD_STEP` 上**，注册在 bridge 之后（例如刷怪导演 `WaveDirector`），与 sim 共用同一个时钟。这样同一种子的结果与帧率无关。
4. `CombatWorld` 的接口签名不变；`api.ts` 中「每帧顺序」的说明改为「每个物理步」。

## 后果

- 击退距离在 30/60/120/144 fps 下都与数据一致（#24 单测）；真实 Arcade 在 60 Hz 和 120 Hz 物理步长下，误差都小于 0.5 px（#26 e2e）。
- 手动暂停、切后台时 Arcade 不推进，sim 和刷怪也就跟着停住，不需要另外处理。
- 物理步长可以按需调整（例如 120 Hz 屏幕顿挫时把 Arcade 的 `fps` 提到 120），sim 的结果不受影响，代价是物理计算量随之增加。
- 渲染帧里读到的 sim 状态（HUD、调试面板）是最近一个物理步的结果，最多落后一个物理步。
